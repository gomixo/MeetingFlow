🎙️ MeetingFlow 四阶段流水线

一段长达数小时的会议录音，是如何一步步变成结构化文字稿的？

📌 一句话总结：MeetingFlow 把录音变成文字稿的过程就像工厂流水线 —— 先拆开包装看规格（探测）、再统一规格（标准化）、再听写内容（转写）、再标注是谁说的（说话人识别）、最后排版成稿（渲染）。

⏱️ 整段录音流向：OBS 录好的原始文件 → 4 个阶段顺序处理 → 输出 speakers.md / speakers.srt

阶段 0/4

🔍 媒体探测（probe）

src/meetingflow/audio.py
输入
OBS 录好的原始文件（.mkv / .mp4 / .wav …）
➡️
输出
source.json（包含时长、采样率、声道、码率等元信息）

做什么

调用 ffprobe 读取文件"包装信息"——这个文件到底是什么编码？多长？几路声道？采样率多少？它不处理音频内容，只读取"身份证"。

// 实际产出示例（pipeline.py:329 写入 source.json）
{
  "path": "D:/Meetings/Inbox/周会-0721.mkv",
  "sha256": "a3f5c8...",
  "size": 524288000,
  "mtime": 1721568000.0,
  "media": {
    "format_name": "matroska,webm",
    "duration_seconds": 3725.4,    // 约 62 分钟
    "sample_rate": 48000,          // OBS 默认 48kHz
    "channels": 2,                 // 双声道
    "bit_rate": 128000,
    "warnings": []
  }
}

为什么要做

想象一下快递员送包裹 —— 他第一件事是先看一眼包裹上的标签（大小、重量、易碎品？），才知道要不要小心搬运。同样，后续阶段需要先确认：

  • 这个文件到底是不是合法音频？万一是损坏文件、空文件、纯视频文件，后面所有步骤都是白跑。
  • 有多长？1 小时的录音和 5 小时的录音处理时间天差地别。
  • 是什么编码？OBS 可能录成 MKV 容器 + Opus 编码，也可能录成 MP4 + AAC，必须先把规格探明。
  • 失败要早暴露：文件少了、被占用、损坏 —— 在阶段 0 就立刻报错，而不是等转写跑到 90% 才崩。

怎么做

本质上就是命令行跑一次 ffprobe：

ffprobe -v error -show_format -show_streams -of json 周会-0721.mkv ↓ 解析 JSON：找 streams 里 codec_type == "audio" 的那条 ↓ 取出 duration / sample_rate / channels / bit_rate ↓ 若任一字段 ≤ 0，抛 "媒体信息不完整"
💡 关键细节：这一步是 纯只读，绝不修改源文件，遵守 AGENTS.md 的"原始录音只读"原则。
阶段 1/4

🎚️ 音频标准化（normalize）

src/meetingflow/audio.py
输入
原始录音 + 阶段 0 的元信息
➡️
输出
audio-16k-mono.wav（16kHz / 单声道 / float32）+ 最大音量分贝数

做什么

把所有音频"翻译"成 AI 模型唯一能听懂的格式：采样率 16kHz、单声道、float32 PCM。无论你录的是 48kHz 立体声 MKV 还是 44.1kHz 双声道 MP3，出来都变成统一规格的 WAV 文件。

// FFmpeg 实际调用命令（audio.py:61）
ffmpeg -y -hide_banner -i 周会-0721.mkv \
    -vn          \    # 不要视频
    -ac 1        \    # 声道数 = 1（合并左右声道）
    -ar 16000    \    # 采样率 = 16000 Hz
    -c:a pcm_f32le \  # 编码 = 32位浮点 PCM
    -af volumedetect \ # 同时检测最大音量
    -f wav       \    # 容器 = WAV
    audio-16k-mono.wav

为什么要做

这是整个流水线最容易被低估、但最关键的一步。背后的逻辑是：

  • 🗣️ 人耳 vs 机器耳：人类听 44.1kHz 立体声觉得"音质好"，但 Whisper/pyannote 这类语音模型训练时只用 16kHz 单声道。喂给它其他格式，要么报错，要么精度下降。
  • 📉 体积大降：62 分钟的 48kHz 立体声 ≈ 700 MB；标准化后只有 ≈ 230 MB。后续转写阶段要反复读盘，节省时间明显。
  • 🔁 一次标准化，多次复用：阶段 2（转写）和阶段 3（说话人识别）都要读这个 WAV。如果不标准化，每个阶段都要重复一次转换。
  • ⚡ 流式 + 原子写入：FFmpeg 直接流式写到磁盘（不是先全读进内存），再原子重命名 —— 即使中途断电也不会留半个文件。
  • 🔊 顺便量音量：用 FFmpeg 自带的 volumedetect 滤镜一次跑完，省一次进程开销；若发现 -inf dB，立刻知道是纯静音录音，避免后面白跑模型。

怎么做

调用一次 FFmpeg 进程，把音频"重新打包"成模型认识的样子：

原始 .mkv (48kHz 立体声 Opus) │ │ ffmpeg 转码 ▼ .tmp 临时文件（流式写入，避免内存爆掉） │ │ atomic rename（只有写完才改名为正式名） ▼ audio-16k-mono.wav (16kHz 单声道 float32) │ │ stderr 中正则匹配 max_volume: -X.X dB ▼ 记入 source.json.max_volume_db 字段（用于排查"为什么没声音"）
阶段 2/4

📝 语音转写（transcribe）

src/meetingflow/transcribe.py
输入
audio-16k-mono.wav + 配置（模型大小、语言、batch、惩罚参数等）
➡️
输出
transcript.raw.json —— 每段带词级时间戳的文字

做什么

这是流水线的"重头戏"。让 WhisperX 模型把音频一字不漏听写下来，并精确标注每个词出现和结束的时间（精度到几十毫秒）。

这一阶段内部其实分两小步：

  1. 2a 听写：Whisper large-v3 模型把音频切成 30 秒一帧，逐帧生成中文文本。
  2. 2b 词级对齐：用 wav2vec2 对齐模型，把每段文字里的每个字/词对应到具体时间戳上。
// 实际产出示例（transcript.raw.json 节选）
{
  "language": "zh",
  "segments": [
    {
      "start": 12.45,
      "end": 15.82,
      "text": " 我们今天主要讨论一下排期问题",
      "words": [
        {"word": "我们",   "start": 12.45, "end": 12.91},
        {"word": "今天",   "start": 12.91, "end": 13.37},
        {"word": "主要",   "start": 13.37, "end": 13.74},
        {"word": "讨论",   "start": 13.74, "end": 14.20},
        {"word": "一下",   "start": 14.20, "end": 14.50},
        {"word": "排期",   "start": 14.50, "end": 15.05},
        {"word": "问题",   "start": 15.05, "end": 15.82}
      ]
    }
  ]
}

为什么要做

没有这一步，后面就完全谈不上"会议纪要"了。但为什么要选 WhisperX 而不是直接用 OpenAI 的 Whisper？

  • 🎯 词级时间戳是后面说话人识别的"胶水"：阶段 3 只会告诉你"0–60 秒是 A 在说话、60–120 秒是 B 在说话"，但不会告诉你 A 说了哪个词。你需要把词的开始时间映射到说话人的时间段上，才能拼出"A 说：我们今天主要讨论……"。这一步能省下 WhisperX 内置的 diarization 调用，由项目自己控制。
  • 🏠 完全本地：模型在本地 RTX 4060 上推理，不上传任何音频或文字，遵守 V1 边界。
  • 🧠 大模型更准：默认 large-v3 是 Whisper 当前最强开源中文模型；用 int8_float16 量化兼顾速度与显存。
  • 🛠️ 可调参数：支持 repetition_penalty、no_repeat_ngram_size 等参数应对 Whisper 著名的"重复幻觉"问题（详细背景见 docs/转录质量问题诊断与改进建议.md）。
  • ♻️ 串行释放显存：AGENTS.md 明确"RTX 4060 8GB 上模型串行加载"，所以转写完立刻 del model; torch.cuda.empty_cache()，给阶段 3 留足空间。

怎么做

两个模型接力：

audio-16k-mono.wav │ ▼ [2a] Whisper large-v3（ASR） │ 按 30 秒切片 + batch=4 流式推理 │ 输出：segment + text（无时间戳） ▼ [2b] wav2vec2 对齐模型（强制对齐） │ 对每个字 / 词精确打上 start / end ▼ transcript.raw.json（带词级时间戳）
💡 重要细节：这里的转写结果还不知道是谁说的，只是"谁在什么时间说了什么字"。说话人标签要等到阶段 3 之后才贴上去。
阶段 3/4

👥 说话人识别（diarize）

src/meetingflow/diarize.py
输入
audio-16k-mono.wav + HF_TOKEN（Hugging Face 令牌）
➡️
输出
speakers.json —— 一系列"时间段 → 发言人标签"片段

做什么

回答一个问题：这段录音里，到底有几个人在说话？每个人在哪个时间区间？

pyannote 模型会输出像下面这样的片段列表：

[
  {"start":  0.0,  "end": 12.4, "speaker": "SPEAKER_00"},
  {"start": 12.4, "end": 35.1, "speaker": "SPEAKER_01"},
  {"start": 35.1, "end": 51.8, "speaker": "SPEAKER_00"},
  {"start": 51.8, "end": 68.5, "speaker": "SPEAKER_02"},
  ...
]

为什么要做

这是会议场景的核心需求 —— 没做这一步，输出就只是"一个人自言自语 60 分钟"的连续文字稿。做了之后，才能区分"谁说了什么"，会议纪要才有意义。

  • 🧩 与阶段 2 互补：阶段 2 告诉你"12.45 秒开始说了'我们今天主要讨论'"，阶段 3 告诉你"12.4–35.1 秒是 SPEAKER_01 在说话"。两者合并才得到"SPEAKER_01 在 12.45 秒说：我们今天主要讨论"。
  • 🔍 不依赖人脸 / 名字：只用声纹特征区分 —— 即便两个人声音很像也能分开；输出只是 SPEAKER_00/01/02，真实姓名由用户事后在 speaker-map.toml 里手动标注。
  • 🤖 模型自带的四步流水线：pyannote 内部做 ① 语音活动检测 → ② 统计说话人数 → ③ 提取每段声纹 → ④ 聚类归组，不用项目自己造轮子。
  • 📦 FFmpeg 零拷贝喂数据：不用 torchaudio 加载（避免后端依赖问题），直接 FFmpeg 解码成 raw float32，再用 torch.frombuffer 零拷贝包装为张量喂给模型。

怎么做

pyannote 的四步内部流水线 + 时间戳对齐：

audio-16k-mono.wav │ │ FFmpeg 解码 → stdout raw float32 bytes ▼ torch.frombuffer(...) 零拷贝成 [1, samples] 张量 │ ▼ pyannote Pipeline({"waveform":..., "sample_rate":16000}) │ ├─► ① 语音分段（VAD）：把音频切成"有人说话"的片段 ├─► ② 统计说话人数 ├─► ③ 提取声纹（speaker embedding） └─► ④ 聚类：把声纹相近的片段归到同一个 SPEAKER_XX │ ▼ annotation.itertracks(yield_label=True) │ ▼ speakers.json: [{start, end, speaker}, ...]

🧩 阶段 3 之后的关键步骤：把"词"和"说话人"绑在一起

这个绑定动作在 pipeline.py 的 _assign_word_speakers 里完成，它对每个词，找与这个词时间重叠最多的说话人片段，然后贴上 speaker 字段，结果存到 transcript.aligned.json。

transcript.raw.json (words + 时间戳) + speakers.json (时间区间 + 说话人) ↓ 对每个 word：找与 [word.start, word.end] 重叠最长的 speaker 段 ↓ word["speaker"] = "SPEAKER_01" ↓ transcript.aligned.json（带说话人标签的词级转写）
阶段 4/4

📄 渲染输出（render）

src/meetingflow/render.py
输入
transcript.aligned.json + speakers.json + speaker-map.toml
➡️
输出
speakers.md、speakers.srt —— 人可直接读的成品

做什么

把所有数据"排版"成人类可读的格式。这一阶段 不再调用任何 AI 模型，纯字符串拼接。

// 输出示例：speakers.md
# 发言人转写

[00:00:12.450] Speaker 1: 我们今天主要讨论一下排期问题
[00:00:15.820] Speaker 1: 我看了下后端那边的进度
[00:00:20.100] Speaker 2: 我这边测试环境还有点问题
[00:00:35.000] Speaker 3: 要不要把联调时间往后挪一天
...
// 输出示例：speakers.srt（字幕格式）
1
00:00:12,450 --> 00:00:15,820
Speaker 1: 我们今天主要讨论一下排期问题

2
00:00:15,820 --> 00:00:20,100
Speaker 1: 我看了下后端那边的进度

3
00:00:20,100 --> 00:00:35,000
Speaker 2: 我这边测试环境还有点问题
...

为什么要做

  • 🎁 多种格式按需选择：Markdown 适合直接贴笔记、Wiki；SRT 是标准字幕格式，可以导入剪辑软件或字幕播放器。
  • 🧠 词级 vs 段级智能取舍：如果某个段落没有词级说话人标签（异常情况），自动退回"按段找最重叠的说话人"，保证任何阶段产物都能渲染。
  • 🔤 名字可后改：第一遍跑完会生成 speaker-map.toml：
[speakers]
"SPEAKER_00" = "Speaker 1"
"SPEAKER_01" = "Speaker 2"
"SPEAKER_02" = "Speaker 3"

用户用记事本改成真实姓名后，无需重新跑模型，只需 meetingflow render 一条命令就能用新名字重新排版 —— 因为渲染阶段完全不需要模型参与。

怎么做

两个关键算法：

transcript.aligned.json │ ▼ 对每个 segment： ├─ 若有 words[] 且每个 word 都有 speaker： │ → 把相邻同 speaker 的词合并成一行 │ （避免每个字独占一行） └─ 否则退回段级： → 找与 [segment.start, segment.end] 重叠最长的 speaker │ ▼ 按时间排序 + 时间戳格式化 hh:mm:ss.mmm │ ├─► speakers.md（用 . 作为小数点） └─► speakers.srt（用 , 作为小数点，符合 SRT 规范）

🔗 端到端串联：一条录音的完整旅程

OBS 录好的 周会-0721.mkv (700 MB, 48kHz 立体声) │ ▼ 阶段 0：探测 │ ffprobe → source.json（62 分钟 / 48kHz / 立体声 / Opus） │ ▼ 阶段 1：标准化 │ ffmpeg 转码 → audio-16k-mono.wav (230 MB, 16kHz 单声道 float32) │ ▼ 阶段 2：转写 │ Whisper large-v3 → 文字段 │ wav2vec2 对齐 → transcript.raw.json（含每个词的时间戳） │ ▼ 阶段 3：说话人识别 │ pyannote 模型 → speakers.json（每个时间段是哪个 SPEAKER_XX） │ 与 transcript.raw.json 合并 → transcript.aligned.json（每个词都贴上 speaker） │ ▼ 阶段 4：渲染 │ 读 speaker-map.toml 把 SPEAKER_XX 替换成真名 │ → speakers.md / speakers.srt（人类可读的最终成品） │ ▼ 输出文件夹 D:\Meetings\Output\2026-07-22_周会-0721_a3f5c8d2\ ├── speakers.md ✅ 可以直接读 ├── speakers.srt ✅ 可以直接当字幕 ├── transcript.raw.json ✅ 模型原始产物（用于排查 / 重跑） ├── transcript.aligned.json ├── speakers.json ├── audio-16k-mono.wav ├── source.json └── run.jsonl ✅ 每个阶段的耗时、参数、错误堆栈

🎯 整体设计原则

原则在代码里如何体现
原始录音只读 阶段 0 / 1 只读取源文件，从不修改；产物写新路径；阶段 1 用临时文件 + 原子 rename
幂等可重跑 每个阶段都有 fingerprint，参数未变 + 产物存在 → 直接跳过；只有改模型 / 改参数才重跑
RTX 4060 8GB 串行加载模型 每个模型用完 del model; torch.cuda.empty_cache()，绝不同时驻留
错误尽早暴露 阶段 0 启动时立刻检查 FFmpeg / ffprobe；阶段 1 检查 max_volume；阶段 3 启动时检查 HF_TOKEN
失败可恢复 SQLite 记每个阶段状态 + fingerprint；retry <job-id> --from <stage> 可从任意阶段续跑
本地处理，不上传 所有模型本地加载；HF_TOKEN 只用于下载模型权重；音频和文字从不离开本机

🤔 一句话回顾：MeetingFlow 的"4 阶段"本质是 先把录音"翻译"成模型认识的样子（标准化），再让两个 AI 模型接力（听写 + 分人），最后用纯文本处理把结果"排版"成人能直接看的样子。
