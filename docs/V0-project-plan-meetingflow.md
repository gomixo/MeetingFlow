# MeetingFlow Windows 会议录音流水线项目方案

> 历史文档：此方案已被 V1 详细设计取代，其中的总结与旧模型设想不代表当前实现。

## 一、项目定位

本项目建设一套运行在 Windows 本地的“会议音频处理流水线”。

OBS 负责稳定录音；会议结束后，流水线自动完成音频检查、语音转写、发言人区分、文本整理和会议纪要生成，并将结果保存到指定项目目录。

Codex 的角色是开发、维护和迭代这套工具，而不是作为每次处理会议录音时的操作入口。

---

## 二、项目要实现的目标

### 1. 核心目标

将会议录音处理过程从当前的多次手动操作，转变为一套稳定、自动、可复用的本地工作流：

**OBS 完成录音 → 自动发现录音文件 → 高质量转写 → 区分发言人 → 生成会议纪要 → 输出到项目目录。**

最终目标不是实时显示字幕，而是获得高质量、完整、可继续加工的会议资料。

### 2. 具体输出

每次会议处理完成后，至少生成以下文件：

1. 原始音频文件或其归档路径；
    
2. 带时间戳的完整转写文本；
    
3. 区分发言人的对话文本；
    
4. SRT 字幕文件；
    
5. Markdown 格式的会议原始记录；
    
6. 结构化会议纪要；
    
7. 处理日志，包括使用的模型、处理时间和异常信息。
    

### 3. 长期目标

随着项目迭代，逐步实现：

- 自动识别会议所属项目；
    
- 根据不同项目调用不同纪要模板；
    
- 自动调用项目背景资料辅助总结；
    
- 自动将结果归档到 Obsidian 或项目文件夹；
    
- 支持人工修正发言人姓名；
    
- 对失败任务进行提示和重新处理。
    

---

## 三、项目边界

### 1. 录音功能不纳入 Pipeline

录音继续由 OBS 完成，不自行开发录音程序。

原因是录音涉及麦克风、系统声音、虚拟声卡、音频驱动和采样率等底层问题。OBS 已经具备较成熟的录音能力，Pipeline 没有必要重复建设。

Pipeline 从“已经生成的音频文件”开始工作。

### 2. 不以实时字幕为目标

本项目不优先实现实时转写，也不要求会议过程中显示字幕。

处理策略以会后高质量处理为主，允许使用更高精度但速度相对较慢的模型。

### 3. 第一阶段不开发完整 GUI

初期不建设复杂的 Windows 桌面界面。

优先采用：

- 文件夹自动监听；
    
- 文件拖拽到批处理入口；
    
- PowerShell 命令行；
    
- Windows 右键菜单。
    

后期确有需要时，可以增加一个轻量界面，用于查看任务状态、选择项目、修正发言人和重新运行任务。

### 4. 不绑定具体业务项目

Pipeline 是通用能力，不属于“中天数科项目”或其他单一项目。

不同业务项目只负责提供：

- 项目名称；
    
- 输出目录；
    
- 会议纪要模板；
    
- 项目背景资料；
    
- 专业词汇表；
    
- 发言人名单。
    

底层的音频处理能力保持统一。

### 5. Codex 不作为日常运行入口

Codex 主要负责：

- 编写和修改代码；
    
- 安装与更新模型；
    
- 排查错误；
    
- 优化处理效果；
    
- 增加新功能。
    

日常处理会议时，不需要打开 Codex，也不需要每次重新向 Codex描述任务。

## 四、用户操作需求

### 1. 理想操作流程

用户的日常操作尽量压缩为以下几步：

1. 打开 OBS；
    
2. 开始会议录音；
    
3. 会议结束后停止录音；
    
4. Pipeline 自动检测录音已完成；
    
5. 系统自动执行后续处理；
    
6. 用户在项目目录中查看转写文本和会议纪要。
    

在理想状态下，停止 OBS 录音之后，用户不需要继续进行其他操作。

### 2. 自动监听模式

由于 OBS 仅用于会议录音，可以直接监听 OBS 的录音输出目录。

监听程序发现新文件后，不立即处理，而是确认：

- 文件扩展名属于支持范围；
    
- 文件大小连续多次不再变化；
    
- OBS 已经释放文件占用；
    
- 文件能够被正常读取；
    
- 音频时长和文件大小合理。
    

确认录音完成后，Pipeline 才开始处理。

### 3. 手动补充入口

除自动监听外，仍应保留以下入口：

#### 文件拖拽

将音频文件拖到 `run.bat` 文件上，系统自动处理该文件。

适用于：

- 手机录音；
    
- 腾讯会议导出的音频；
    
- 旧录音补处理；
    
- 自动监听未触发的文件。
    

#### 命令行运行

通过 PowerShell 输入音频路径和项目参数。

适用于：

- 测试；
    
- 排错；
    
- 批量处理；
    
- 指定特殊模型或模板。
    

#### 重新处理

用户可以选择：

- 只重新转写；
    
- 只重新识别发言人；
    
- 只重新生成纪要；
    
- 更换模型后重新运行完整流程。
    

### 4. 项目归属处理

第一阶段可以采用简单规则：

- 根据录音文件所在文件夹确定项目；
    
- 或在文件名中加入项目代号；
    
- 或为不同项目设置不同的输入目录。
    

例如：

```text
D:\Meetings\中天数科\Inbox
D:\Meetings\快速路指挥中心\Inbox
D:\Meetings\其他项目\Inbox
```

Pipeline 根据输入目录自动选择对应的配置和纪要模板。

## 五、系统工作流程

完整工作流程建议拆分为以下步骤：

### 第一步：发现录音

监听 OBS 输出目录，识别新生成的录音文件。

### 第二步：确认录音完成

检测文件大小是否稳定、文件是否仍被占用，避免在 OBS 尚未完成写入时提前处理。

### 第三步：音频预检查

检查：

- 音频能否正常打开；
    
- 实际时长；
    
- 采样率；
    
- 声道数；
    
- 音量是否异常；
    
- 是否存在明显加速、变调或损坏。
    

必要时将音频转换为统一格式，例如标准 WAV 或其他适合模型处理的格式。

### 第四步：语音转写

通过本地模型生成：

- 完整文本；
    
- 分段时间戳；
    
- SRT 字幕。
    

转写模型可以先使用 Whisper 系列或其他适合中文会议的本地模型，后续通过实际测试确定最终方案。

### 第五步：发言人区分

对音频执行 Speaker Diarization，识别：

- Speaker 1；
    
- Speaker 2；
    
- Speaker 3；
    
- 各发言人的时间范围。
    

再将发言人结果与转写文本合并。

第一阶段不要求系统准确识别真实姓名，但应允许用户将 Speaker 1、Speaker 2 手动映射为具体人员。

### 第六步：文本整理

自动处理：

- 重复语句；
    
- 无意义语气词；
    
- 错误断句；
    
- 专业术语；
    
- 中英文混排；
    
- 时间戳与发言人的对应关系。
    

同时保留一份未经大幅润色的原始转写稿，避免信息在整理过程中丢失。

### 第七步：会议总结

根据会议所属项目调用对应模板，生成：

- 会议主题；
    
- 参会人员；
    
- 背景与目标；
    
- 讨论内容；
    
- 关键结论；
    
- 已确认事项；
    
- 未决问题；
    
- 风险与分歧；
    
- To Do List；
    
- 负责人和时间要求。
    

### 第八步：结果归档

处理结果写入对应项目目录，并保留任务日志。

## 六、实施路径

### 阶段一：解决录音稳定性

首先确认当前录音时间压缩、声音变快的问题。

重点检查：

- OBS 采样率；
    
- Windows 音频设备采样率；
    
- 虚拟声卡采样率；
    
- 编码格式；
    
- 音频文件实际时间戳。
    

建议将 OBS、Windows 麦克风、系统输出和虚拟声卡的采样率统一，例如统一设置为 48 kHz。

在录音稳定性没有解决之前，不进入大规模自动化开发。

### 阶段二：建立最小可用 Pipeline

先实现一个命令行版本：

```text
输入：一个音频文件路径
输出：TXT、Markdown、SRT
```

这一阶段只完成：

- 音频格式检查；
    
- 本地转写；
    
- 基础时间戳；
    
- 文件输出；
    
- 日志记录。
    

先验证转写模型的准确率和运行速度。

### 阶段三：增加发言人识别

接入发言人区分模型，将转写结果和发言人时间段进行合并。

这一阶段重点验证：

- 两人会议；
    
- 三人以上会议；
    
- 现场声音与远程声音混合；
    
- 发言重叠；
    
- 音质较差的情况。
    
- 发言人总结要注意识别出来数量和实际发言人数量不符合的情况

### 阶段四：加入 OBS 文件夹自动监听

建立 Windows 后台监听程序。

触发逻辑不能仅仅是“文件出现”，而应是：

```text
发现文件
→ 等待文件大小稳定
→ 检查文件未被占用
→ 验证音频可读取
→ 加入任务队列
→ 开始处理
```

同时保留拖拽和命令行入口作为备用方式。

### 阶段五：接入会议总结

将转写稿发送给本地或在线大模型，按照预设模板生成会议纪要。

不同项目采用不同配置文件，不修改底层代码。

### 阶段六：建立项目配置体系

每个项目设置独立配置，例如：

```text
项目名称
输入目录
输出目录
会议纪要模板
专业词汇表
常见参会人员
项目背景资料目录
```

Pipeline 根据录音来源自动加载对应配置。

### 阶段七：逐步提高自动化程度

后续可以增加：

- 自动识别项目；
    
- 自动修正专业术语；
    
- 自动匹配发言人姓名；
    
- 批量处理；
    
- 失败重试；
    
- Windows 开机自启动；
    
- 系统通知；
    
- Obsidian 自动归档；
    
- 轻量任务管理界面。

## 七、需要注意的事项

### 1. 录音质量优先于模型能力

如果原始录音存在丢帧、变速、回声、音量过低或多路声音互相覆盖，再强的转写模型也难以得到稳定结果。

因此第一优先级是保证 OBS 输出文件完整、时长正确、声音自然。

### 2. 统一音频参数

OBS、Windows 音频设备、虚拟声卡应尽量使用统一的采样率和声道配置。

每次调整录音链路后，应先录制一段 5—10 分钟测试音频，核对：

- 实际时长；
    
- 播放速度；
    
- 人声是否变调；
    
- 本地和远程声音是否完整。
    

### 3. 防止处理未完成的录音文件

监听程序必须判断文件是否已经写入完成，不能在文件刚出现时立即转写。

建议同时使用：

- 文件大小稳定检测；
    
- 文件占用检测；
    
- 最短等待时间；
    
- 音频完整性检查。
    

### 4. 防止重复处理

每个任务需要有唯一标识，并记录处理状态：

```text
待处理
处理中
处理成功
处理失败
需要人工检查
```

同一文件已经成功处理后，除非用户明确要求，否则不应重复运行。

### 5. 保留原始材料

不能只保留 AI 整理后的纪要。

至少应同时保留：

- 原始音频；
    
- 原始转写稿；
    
- 发言人版本；
    
- 最终会议纪要；
    
- 处理日志。
    

这样才能在总结出现错误时回溯原始信息。

### 6. 发言人识别不是绝对准确

多人同时说话、距离麦克风较远、回声和远程声音混合，都可能影响发言人区分。

系统应允许用户快速修改：

```text
Speaker 1 → Viktor
Speaker 2 → 中天数科项目负责人
Speaker 3 → 技术负责人
```

### 7. 专业术语需要项目词汇表

工程、能源和项目管理会议中会出现大量企业名称、设备名称和专业缩写。

应为不同项目维护专业词汇表，以提高转写和后续纠错质量。

### 8. 总结模型不能代替原始转写

AI 生成的纪要可能发生遗漏、归纳错误或责任人判断错误。

涉及重要决策、金额、时间节点和责任分工的内容，应能够快速返回原始时间戳核对。

### 9. 注意本地资源消耗

转写和发言人识别可能占用较多 GPU、CPU、内存和磁盘空间。

Pipeline 应：

- 控制同时处理的任务数量；
    
- 支持任务队列；
    
- 记录模型运行失败原因；
    
- 避免会议结束后多个大模型同时抢占资源。
    

### 10. 数据安全与隐私

会议录音通常包含客户信息和项目资料。

默认应优先采用本地处理。需要调用在线模型时，应明确：

- 哪些文件会上传；
    
- 上传的是原始音频还是转写文本；
    
- 是否进行脱敏；
    
- 文件是否包含敏感信息。

## 八、最终推荐架构

```text
OBS
│
│ 生成会议录音
▼
OBS 录音目录
│
│ Windows 文件监听器
▼
会议处理 Pipeline
├── 文件完成检测
├── 音频检查与格式转换
├── 语音转写
├── 发言人区分
├── 文本整理
├── 会议总结
└── 日志与异常处理
│
▼
对应项目目录
├── 原始音频
├── 原始转写
├── 发言人转写
├── SRT 字幕
├── 会议纪要
└── 处理日志
```

这套方案的核心原则是：

**OBS 负责可靠地录，Pipeline 负责高质量地处理，Codex 负责持续开发和维护。**

先把录音稳定、单文件转写和发言人识别做好，再逐步加入自动监听、项目模板和会议纪要生成，避免第一版建设过度复杂。
