# 转录质量问题诊断与改进建议

## 1. 背景

使用同一份约 1 小时 38 分钟的录音，对比了 OPPO 转录结果与 MeetingFlow 生成的 `speakers.md`。MeetingFlow 能覆盖完整录音和主要讨论脉络，但在以下方面明显弱于 OPPO：

1. 个别片段出现长串重复字，即重复幻觉；
2. 部分长片段存在疑似漏字和语义跳跃；
3. 一段转写中发生说话人切换时，整段仍被标记为同一个人；
4. 人名、机构名和专业术语识别不稳定。

本次分析基于两份转录文本、MeetingFlow 原始任务产物和当前实现。由于没有人工校对稿，文中的准确性判断属于文本互证和实现诊断，不是严格的字错率测量。

## 2. 结论

当前不应优先更换 `large-v3` 模型。主要问题来自 WhisperX 批量转写方式和 MeetingFlow 的说话人渲染流程：

| 问题 | 主要根因 | 判断 |
|---|---|---|
| 重复幻觉 | WhisperX 批量解码没有有效使用失败检测和温度回退，且未限制重复 | 主要是解码流程问题 |
| 疑似漏字 | VAD 合并成长语音块后独立解码，弱语音、重叠语音可能被跳过 | 分段与模型共同影响 |
| 说话人边界合并 | 每个完整转写段只选择重叠时间最长的一个说话人 | 明确是 MeetingFlow 流程问题 |
| 人名和术语错字 | 通用模型缺少会议领域词和上下文提示 | 模型通用能力问题 |

推荐按“说话人分配 → 重复控制 → VAD 验证 → 解码路径”的顺序处理。

## 3. 诊断依据

### 3.1 重复内容来自原始转写

以下异常已经存在于任务目录的 `transcript.raw.json` 中：

- `00:41:55`：连续 58 个“深”；
- `00:45:33`：连续 116 个“对”；
- `00:54:53`：连续 39 个“嗯”；
- `01:32:32`：连续 37 个“框”。

因此，重复幻觉发生在 WhisperX 转写阶段，不是词级对齐、pyannote 说话人识别或 Markdown 渲染造成的。

当前 WhisperX 3.8.6 的批量管线虽然配置了压缩率阈值、低概率阈值和多温度回退，但批量生成路径主要执行一次 beam search，没有完整应用这些失败回退逻辑。同时当前默认值为：

```text
repetition_penalty = 1
no_repeat_ngram_size = 0
condition_on_previous_text = false
```

这使长语音块在解码进入循环后缺少有效的退出机制。

### 3.2 最终文档没有主动删除转写内容

`render_speakers_markdown` 会遍历 `transcript.raw.json` 中的所有转写段，并原样输出每段的 `text`。因此，如果核听后确认存在漏字，根因应继续在 VAD 或 ASR 阶段查找，而不是修改 Markdown 渲染器补偿。

当前 WhisperX 默认使用约 30 秒的 VAD 合并块，每个块独立解码。多人快速交替、同时发言或声音较弱时，单次解码可能跳过部分内容。

### 3.3 说话人边界在渲染阶段丢失

当前 `render._speaker_for` 为一个完整转写段计算与所有 pyannote 片段的重叠时长，然后只选择重叠最长的说话人。

本次录音中，`53.295–79.097` 是一个约 26 秒的转写段。pyannote 在这个范围内已经识别出多次说话人切换，但最终文档仍把整段归给一个 Speaker。说明说话人模型并非完全没有识别边界，而是渲染时丢弃了段内边界。

## 4. 改进方案

### P0：按词级时间戳分配说话人

这是根因明确、收益确定的第一优先级。

处理方式：

1. 使用 WhisperX 对齐结果中每个词的 `start` 和 `end`；
2. 使用 WhisperX 已有的 `assign_word_speakers` 将词分配给 pyannote 说话人；
3. 当相邻词的说话人发生变化时拆分输出行；
4. 将连续属于同一说话人的词重新合并；
5. 对缺少时间戳的标点或词，跟随最近的有效说话人。

已知会议人数时，可以把 `min_speakers` 和 `max_speakers` 设置成相同值来稳定聚类。但这只能改善 pyannote 聚类，不能替代词级拆分。

### P1：限制重复并缩短转写块

先使用现有 WhisperX 和 `large-v3` 做最小参数调整：

```python
asr_options = {
    "repetition_penalty": 1.1,
    "no_repeat_ngram_size": 3,
}
```

同时将转写调用的 `chunk_size` 从 30 秒试降到 20 秒。

这些值应先用于代表性片段 A/B 测试，不应未经核听直接固化。`no_repeat_ngram_size` 过大会误伤正常重复表达，块过短也可能损失上下文。

不要仅在输出阶段删除重复字符。后处理可以识别异常并触发重试，但直接删除只能隐藏幻觉，无法恢复被覆盖的真实语音。

### P2：核听确认漏字后再调整 VAD

建议从整段录音选取弱音、多人交替、背景噪声和正常语音片段，核对原始音频与 `transcript.raw.json`。只有确认语音没有进入转写段时，才调整 VAD。

可试验的最小变化：

```text
vad_onset: 0.50 → 0.40
chunk_size: 30 → 20
```

降低 `vad_onset` 可以捕获更多弱语音，也会增加噪声进入转写的概率，因此必须用核听结果决定，不应只根据文本长度判断。

`batch_size` 主要影响速度和显存，降为 1 仍然使用 WhisperX 的同一批量解码实现，不能恢复缺失的失败回退逻辑，不应作为主要质量开关。

`compute_type` 可以从 `int8_float16` 对比测试 `float16`。它可能带来小幅准确率改善，但不会单独解决重复幻觉和段内说话人合并。

### P3：必要时改用标准 faster-whisper 解码

如果 P1、P2 后仍有明显重复或漏字，可将转写阶段改为标准 `faster-whisper` 顺序解码，继续复用现有 WhisperX 词级对齐和 pyannote 说话人识别。

这一方案仍使用 `large-v3`，但可以使用更完整的低概率检测、压缩率检测、温度回退、上下文衔接和词级时间戳。代价是转写时间可能增加，需要在质量改善确认后再决定是否替换当前批量路径。

该变化属于核心转写流程调整，实施前应确认影响和最小方案。

### P4：补充领域词提示

在人名、公司名和业务术语的主要流程稳定后，再增加可选的 `initial_prompt` 或 `hotwords`，例如会议中高频出现的人名、机构名和“数字化转型”“生命线”等术语。

领域词应按任务配置，不应写死在代码中。提示过多或权重过强可能反向诱发幻觉，因此优先级低于前述结构性问题。

## 5. 验证方案

先建立一个小型、可重复的人工验收集，不需要一开始就重跑全部录音：

1. 从本次录音选取四个已知重复异常片段；
2. 再选取四个正常、弱音、多人交替和数字密集片段；
3. 每段保留约 30–60 秒人工校对文本；
4. 对当前参数、P1 参数和必要时的标准 faster-whisper 路径进行 A/B；
5. 选定方案后再完整处理 98 分钟录音。

建议验收指标：

- 不再出现连续 10 个以上相同汉字的解码循环；
- 人工抽查的说话人切换点能够按词级边界拆分；
- 对固定校对片段计算 CER，而不是使用另一台设备的转录作为绝对真值；
- 核查数字、人名、机构名和专业术语；
- 记录完整录音的处理耗时和峰值显存，避免质量调整破坏 RTX 4060 8GB 的可运行性。

## 6. 推荐实施顺序

1. 修复词级说话人分配和输出拆分；
2. 加入重复限制，将 `chunk_size` 试调为 20 秒；
3. 用短片段 A/B 核听，确认漏字究竟来自 VAD 还是 ASR；
4. 必要时调整 VAD；
5. 如果批量转写仍不稳定，再改用标准 faster-whisper 顺序解码；
6. 最后增加可选领域词提示。

本阶段不建议直接更换核心模型，也不建议为单次会议引入新的模型依赖。
